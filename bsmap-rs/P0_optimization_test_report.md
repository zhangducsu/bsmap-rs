# BSMAP-rs P0 性能优化测试报告

## 概述

本次测试针对 BSMAP-rs 进行了 P0 级别的 SIMD 优化，并重新在 Docker 环境下运行了 Ex1 和 Ex2 的完整基准测试。目标是验证我们的 SIMD 优化是否提升了性能，同时保持 BSMAP C++ 原有的 SAM 比对一致性。

## 优化内容总结

| 优化项 | 状态 | 说明 |
|-------|------|-----|
| xc32/x64 SIMD 批量处理 | ✅ 已完成 | 支持 AVX2 SIMD，一次 8/4 个值 |
| xm64 SIMD 批量处理 | ⚠️ 部分完成 | 使用 SIMD 框架，但实际为标量（为了兼容性） |
| xt3/xt3_64 SIMD | ❌ 未进行 | 算法复杂度高，需要重新设计 |
| WGBS 索引整合 | ❌ 未进行 | 数据结构需要大量重写 |
| 边界检查优化 | ❌ 未进行 | 安全与性能权衡 |

## 问题分析

### 为什么 Ex1 有提升但 Ex2 反而变慢？

可能的原因：
1. **xc/xm 函数调用量**：Ex1 和 Ex2 中 xc/xm 函数的调用频率可能不同
2. **索引加载时间**：本次测试索引加载占用更多时间（约 12s vs 之前更快）
3. **系统负载波动**：Docker 环境下的系统负载差异可能导致性能波动
4. **SIMD 优化影响范围**：我们目前仅优化了独立的 xc/xm 函数，但实际调用点可能未批量处理

### 为什么优化幅度有限？

1. **核心瓶颈仍在 xt3 函数**：xt3 是最耗时的哈希计算函数，但我们未对其优化
2. **SIMD 优化未在热点路径实际应用**：我们添加了 xc32_simd_batch 等函数，但代码库中实际比对逻辑可能未使用它们
3. **内存和 I/O 成为瓶颈**：索引加载和内存访问占用较多时间

## 优化建议（优先级顺序）

### P0 必做（高优先级）

1. **批量优化实际比对流程**
   - 分析当前比对流程的热点路径
   - 将 xc/xm 调用改为批量调用
   - 实际集成我们实现的 SIMD 函数

2. **xt3 函数优化**
   - 寻找算法层面简化或预计算机会
   - 分析 xt3 计算量最大的部分（位操作和乘法）
   - 考虑查表法等优化手段

### P1 重要（中优先级）

3. **WGBS 索引结构优化**
   - 整合 index2/positions/start_offsets
   - 提高缓存局部性

4. **热点路径安全检查去除**
   - 在明确安全的热点路径减少或避免边界检查

### P2 一般（低优先级）

5. **多线程优化**
   - 确保 -p N 参数正确生效
   - 分析多线程扩展性
